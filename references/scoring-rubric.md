# 评分量表｜Score with Reasons, Not Vibes

## A. 先确定评分对象（必须）

清楚写下：**被评对象、原始目标、评估阶段、证据范围**。评分必须对应对象与阶段：

- 成品审查（`audit`）：评要求覆盖、结果证据与可交付性；不能因为过程辛苦而加分。
- 观点挑战（`challenge`）：评论证是否成立、反证处理与适用边界；不评个人能力或人格。
- 准备阶段（`preflight`）：评需求、假设和验收门槛是否明确；尚未发生的成果不得打已完成分。
- 失败预演（`premortem`）：评方案的风险识别与控制准备程度，不把虚构失败当作事实。
- 苏格拉底对话（`dialogue`）：默认不评分；形成可检查方案后可应用户要求评分。
- 创作/审美：评**与用户意图的匹配**、内部一致性、原创表达和明确事实准确性，不以个人趣味冒充客观标准。

### A0. 先打开，再评分（硬前置）

**对象是代码、文件、报告或配置时，必须先实际读取内容再下任何判断。**

- 用 Read / Grep / Bash 等工具真正打开被审对象；引用证据必须带可复核位置（如 `path:line` 或具体章节）。
- **禁止凭对话记忆、文件名猜测、他人转述或摘要代替实际查看。**“我刚生成过这个文件”不构成已核验。
- 同一模型刚写完的成果同样适用——写完不等于读过，更不等于读过改后的版本。
- 确实无法查看（文件不存在、无权限、在远端）→ 直接说明，并给出该对象能拿到的最高分与置信度；**不要给一个看似精确的分数**。
- 凡是没实际打开的检查，一律标 `[未知]`，不得写“通过”。

若无可查看对象或最低限度的成功标准：返回 `暂不评分`，提出最关键缺失证据。不要因用户强求数字而编造。

## B. 通用五维评分（100 权重）

| 代号 | 维度 | 权重 | 评估问题 |
| --- | --- | ---: | --- |
| A | 目标契合与覆盖 | 25 | 真正解决的是否是用户提出的事？硬约束、必需项有遗漏吗？ |
| B | 证据与核验 | 25 | 重要事实、验收或因果主张有对应可信证据吗？没做的验证有没有如实标注？ |
| C | 逻辑与反证 | 20 | 论证能否支持结论？最强反例、替代解释及适用条件得到处理了吗？ |
| D | 约束、风险与取舍 | 15 | 是否正视边界、损失、负面后果与替代选项，而不是只谈收益？ |
| E | 可执行性与表达 | 15 | 结果是否便于使用、验证、继续推进，结构清楚且符合目标受众？ |

每维以 `0、0.5、1 ... 5` 计分。通用锚点：

| 单维分 | 解释 |
| ---: | --- |
| 0 | 缺失、完全无效或相反 |
| 1 | 严重不足，无法支撑目标 |
| 2 | 部分相关，但有明显缺陷 |
| 3 | 基本可用，有重要补充/修复空间 |
| 4 | 良好，仅存在有限、明确的缺口 |
| 4.5 | 优秀，已覆盖主要边界，剩余问题较小 |
| 5 | 高质量且与该阶段所需证据匹配，关键要求无遗留问题 |

**重要**：

1. `B` 维度按**当前阶段应具备的证据**评：计划需要明确可验证假设，不要求计划已经通过量产测试；事实报告需要可靠来源，驱动修复需要对应实验。遗漏必须核实的证据降低 B 分，不得标成 N/A 规避。
2. “证据不存在”不是“结论错误”；可以保留有条件结论，同时降低置信度和 B 分。
3. 一条关键问题可能影响多维，但不要重复扣同一个错误导致重复惩罚；明确其主要所属维度，必要时解释关联。
4. 用户另有明确评分标准时优先采用，列明差异；跨不同评分规则的分数不可直接比较。

## C. 汇总规则

`原始质量分（0–10） = (A×25 + B×25 + C×20 + D×15 + E×15) / 50`。

若五维均为 5，结果为 10；均为 4，则结果为 8.0。用标准四舍五入（half-up）保留一位小数，输出分项和简短依据。脚本可重复复算：

```bash
python scripts/score.py --a 4.5 --b 4 --c 4.5 --d 4 --e 4.5
```

### 严重问题必须落在维度分上

重大原始要求未达、已确认的决定性事实/逻辑错误、关键实测未完成却被声称已解决、编造引用或验证证据——**这些不是额外扣分项，必须体现为对应维度的低分**：

- 关键要求没做到 → `A`（目标契合）显著降低，并明确写出缺失项。
- 结论站不住或与事实冲突 → `C`（逻辑与反证）显著降低。
- 声称已解决但只有编译/理论推断、没有实测 → `B`（证据与核验）显著降低，并标注`尚未验证`。
- 编造来源、工具结果或验证证据 → `B` 直接给最低档，并在裁决里点名。

不要在维度分之外再叠加一个机械的总分上限；一个缺陷只在其主要所属维度扣一次分。
判早期计划按**该阶段应有的证据**评分，不因尚未落地而判失败。

### 置信度是独立维度，不乘分

- **高**：关键材料完整、核心要求大多被直接核验，检查边界清楚，重要数据有可信且尽可能独立的支持。
- **中**：主干可检查，但存在局部未核验内容，结论有适当条件。
- **低**：只看到片段、来源不独立、关键材料缺失或需要用户实测；通常给“暂不评分”或“初评（低置信度）”。

绝不把 `8.8/10` 读作 88% 成功概率，也不说“检测出 88% 的问题”。

## D. 输出层级

输出结构由 `SKILL.md` §5 统一定义（五段式：原始需求 → 审查结论 → 核心依据 → 改进闭环 → 本次评分）。
本节只规定**分数在第五段里怎么写**。

### 评价档位（由总分直接映射，不得凭印象单独给）

| 总分 | 评价 |
| --- | --- |
| 8.5 – 10 | 优秀 |
| 7 – 8.4 | 良好 |
| 5.5 – 6.9 | 一般 |
| < 5.5 | 待改进 |

### quick（尽量不超过五句，不铺表格）

> **结果：部分解决；6.6/10（低置信度）。**
> 改动已核实（`src/main.c:212-236`），但 500 帧高负载实测缺失——这是不能判为已解决的唯一原因。
> **下一步：**跑完 500 帧下发并贴日志，再回来复审。

### deep

第五段展开五维评分表，顺序为：结论与结果 → 五维分数及证据 → 得分依据 → 最终意见。
证据必须带位置（如 `path:line`），未实测的项必须显式标注，不得混入已核验。

**不得用满屏表格掩盖简单结论；也不得因为报告写得更漂亮就把分数调高。**

## E. 自审防作弊提问

在公布分数前，回答：

1. 是否使用了**原始目标**，还是改了一个更容易得高分的目标？
2. 哪项尚未验证可能直接推翻我的高分？
3. 哪一项扣分理由可以由其他人独立复现？
4. 是否因“我自己写的”而忽略明显问题？
5. 这个分数里的**每一条扣分理由**，我是否真的打开过被审对象才写的？

若发现新重大问题，先修正结论与分数，不要为了达到用户设定的目标分修改标准。`9.5` 是需要**证明**的质量门槛，不是预先写好的分数。
